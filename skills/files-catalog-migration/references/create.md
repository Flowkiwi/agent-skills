# Create

Phase 3: from an approved `products.json` and the recorded concepts (`concepts/*.json`) to products in the Flowkiwi tenant. `$S` is `python3 $SKILL/scripts` and `<dir>` the workspace. Schemas below were checked on 2026-10-26. If a call is rejected for an unknown or missing field, run `describe_operation` on it and adapt the argument names; do not guess, and never change a value printed by a script (`## Worker MCP rules`).

## Steps

1. **Blocking check**: `$S/catalog.py --check <dir>/products.json --state <dir>/state.json`. Do not go further while it exits 1: any `duplicate_key`, `duplicate_handle`, `missing_title`, `too_long`, `duplicate_sku`, `missing_sku`, `missing_barcode`, `short_option_name`, `duplicate_option_values`, `missing_option_value`, `list_in_single_field`, or an `unknown_status` (an empty status included) without a `status_map` entry when `status_mode` is `source`. They break the uniqueness lookups (parallel workers would race on the same SKU) or would fail every affected product. Settle them in Phase 2 (`references/products.md` `## Warnings`).
2. **Dry-run summary**: `$S/dryrun.py <dir>` (exit 1 while blocking warnings remain, `status_mode` / `data_language` is missing or `status_mode` is not `draft`, `active` or `source`). Its `Concepts` section has one line per concept file (`concepts/<concept>.json`): taxonomy categories, attribute definitions, options and products without category; collections and products in a collection; one row per metafield definition with the proposed and the chosen type (validate them again: a type cannot change later); metaobject definitions, entries and products referenced; price offers, variant-country pairs without price and countries; each followed by the names it will write, for review in the data language (category paths, attribute definitions with their options, collection paths, metaobject definitions with their fields and reference metafield, entries with their display name, taxes; 20 per kind, then `... and <n> more`; the metafield rows already name their definitions), then by its warnings grouped by code. Its `MCP effort` line estimates the calls after approval and their time (about 8 s per call: shared elements, products with their children, updates of a later phase): tell the developer the MCP time before approval. Its `Blocking` section also lists the concept files extracted from another `products.json` or mapping (their `provenance` block, `references/state.md` `## Concept files`: run the `extract.py` it prints, then record the concept again), the stale decisions (a concept file that differs from its decision in `state.json`, warnings aside: extracted again and not recorded, or never recorded: run the `state.py decide` it prints, with the origin and reason recorded before, after checking the new preview), the `list_in_single_field`, `missing_sku` and `too_long` warnings of the concept files, the created handles no longer in `products.json` (identity changed or product removed: undo it first, `references/undo.md`, or restore its key; in a later phase they are removed products instead, `references/phases.md`), the handles `products.json` and `state.json` disagree on (run `state.py sync`), and the products whose `payload.py` would fail (built with placeholders for every product to create). Show its output: data language, status, counts to create, cleaning counts per rule, **agent choices** (every `"origin": "agent"` of the mappings and decisions, with its reason: the developer validates or corrects each one), generated codes, descriptions with up to 3 generated candidates, what is not migrated. Add the shared elements to create or reuse (`$S/plan_shared.py <dir>`, with every generated name: check none is left in another language than `data_language`), the data kept but not created (images, the concepts not taken, columns not mapped), and 2-3 fully mapped sample products as MCP payloads: `$S/payload.py <dir> <handle> --dry-run` (pick several variants, a generated code or description, the longest description). It prints `<key IRI>` placeholders (`<key UUID>` for the value of a metaobject reference) for shared elements not created yet; IRIs that only exist after an earlier call, like `<product IRI>`, stay placeholders. **Wait for explicit approval.**
3. **Shared elements**: `$S/plan_shared.py <dir>` prints the ordered plan from the decisions with each `body`, `lookup`, `spec` and state key, skipping keys already recorded: one loop covers every concept, in this order: the `import.key` marker definition, categories, attribute definitions and options, collections, metaobject definitions, entries and reference metafield definitions, metafield definitions, taxes (lookups and body details in each concept reference, `## Shared elements`). Create them in this session, or delegate to one dedicated worker (`## Shared elements worker`, its prompt generated by `$S/prompts.py <dir> shared`), looking up before each creation. Record them with `$S/state.py shared <dir> --file <results.json>`, each entry with the `spec` copied from its plan entry (rerun `plan_shared.py --ready` for the entries whose dependencies are now recorded).
4. **Pilot**: `$S/state.py worklists <dir> --workers 1 --pilot` (picks up to 5 representative products: several and single variants, with and without category, generated description, each status, longest description; or `--handles a,b,c` for an explicit choice), then `$S/verify.py sample <dir> --rate 0.1 --output <dir>/verify-sample.json` (pilot products are always in the sample), dispatch the worker (SKILL.md "Running workers"), `$S/state.py merge <dir>`. Show the pilot products (`## Verify`) and ask the developer to check them in Flowkiwi. If something is wrong: undo the pilot (`references/undo.md`, scope `pilot`), fix the mapping or the decision, extract again, `$S/state.py reset-deleted <dir>`, rerun the pilot.
5. **Full run**: `$S/state.py worklists <dir> --workers 4` (default 4, at most 6: more workers hit the MCP rate limit), `verify.py sample` as above, dispatch the workers, `state.py merge`, repeat until no `pending` product remains.
6. **Final report** from `$S/state.py summary <dir>`: created / reused / failed per kind, failures with errors and a retry offer (`state.py worklists <dir> --workers 4 --retry-failed`), description checks (`verify` counts: ok / fixed / mismatch, with the mismatched handles to review by hand), lines rejected by `merge` (`results/rejected-*.jsonl`), generated barcodes and SKUs count, generated keys (products without reference, for the client), decisions per origin and the agent choices to confirm with the client, images not migrated (count; URLs in `products.json`), data kept but not created (prices when the prices concept was not taken, columns not mapped). Then the client review (`references/review.md`): `$S/client_review.py <dir>`, show its counts (questions, choices, missing data items), review the document with the developer and tell them the file to send to the client, `<dir>/client-review.md`.

## Shared elements

The marker definition, before any product (first entry of `plan_shared.py`):

1. `call_operation list_metafield_definitions` with `ownerType` products (every page), then filter namespace `import` and key `key` client side: the operation filters neither namespace nor key.
2. If missing, `call_write_operation create_metafield_definition` with the plan entry `body`, for example in `fr`:
   `{"body": {"namespace": "import", "key": "key", "name": "Clé d'import", "ownerType": "/api/metafield_owner_types/products", "type": "/api/metafield_definition_types/single_line_text_field", "description": "Marqueur technique posé par la migration de fichiers"}}`
   `name` and `description` are in the data language (`plan_shared.py` prints them, `marker_labels` overrides them). The namespace and key stay `import.key` in every language.
3. `$S/state.py shared <dir> --key metafield_definition:import.key --iri <iri> --status created|reused --module core --spec-json '<the plan entry spec>'`.

The other entries follow in the plan order, each recorded with the `module` of its plan entry: lookups and bodies in the `## Shared elements` section of `references/taxonomy.md`, `references/collections.md`, `references/metaobjects.md`, `references/metafields.md` and `references/prices.md`.

## Per product

The worker runs this for each handle of its worklist, in order. Every item created or reused is collected for the result line, with its `module`: `core` for the product, the marker, options and variants, the concept for the others (steps 9 to 11). An item with a `shared` key takes the module of that shared element in `state.json` (`metafields`, `metaobjects` for a reference metafield): `state.py merge` sets it from the state. Each item has its `ref`: the SKU for a `variant`, the option title for a `product_option`, `<option title>:<value>` for an `option_value`, `namespace.key` for a `metafield` (`import.key` for the marker), `<sku>:<country code>` for a `sale_offer`.

**Payloads.** First run `python3 $SKILL/scripts/payload.py <dir> <handle>`: it prints every body below (product with its category, attributes and collections, marker, options, variants, metafields, prices). Build each MCP argument from that output, copying values verbatim: never retype them from `products.json`, never fix spelling, whitespace or HTML, and keep `\uXXXX` escapes as they are in the JSON arguments. Only IRIs returned at runtime (product, options, option values, variants) are added by the worker. If `payload.py` fails (missing decision or shared IRI), fail the product with its message: never guess a value.

**Created vs reused.** An item is `created` when this migration made it: its `createdAt` is at or after `started_at` (compare full timestamps), or it is listed as `created` in `state.json` for this handle. Anything older is `reused`. This matters after a crash: items found again must stay `created` so undo removes them.

1. **Skip** if `state.json` says `created`.
2. **Adopted product**: if `decisions.adopt[<handle>]` exists (the developer chose to map this handle to an existing tenant product during Phase 2), use that product: write the marker (step 6) if missing, record the product `reused`, continue at step 7.
3. **Find by marker**: `list_products` with `query.metafield["import.key"] = <handle>`. Found: record it per the created/reused rule above and only create what is missing (compare options, variants by SKU).
4. **Orphan lookup**, always when the marker lookup found nothing (a previous worker may have died between creating the product and writing its marker): `list_products` with `query.title = <title>` and `query["createdAt[after]"] = <date part of started_at>`. Keep only candidates whose title is **exactly** equal and whose `createdAt` timestamp is at or after `started_at`, then check their metafields (`call_operation list_metafields` on `products/<id>`). A candidate **without** an `import.key` metafield is an orphan of this migration: adopt it (record `created`) and continue at step 6. More than one candidate: fail this product and report it (the developer decides).
5. **Create the product**: `call_write_operation create_product` with the payload `product.body`. **On a timeout, a 5xx or a 429, never retry blindly**: run the orphan lookup (step 4) before each retry (waits and attempts: the MCP rules), and retry the creation only if it finds nothing.
6. **Marker**: `call_write_operation create_metafield` with `path {"ownerResource": "products", "ownerId": <id>}` and the payload `marker.body`. The value is translatable: never pass `locale`, so it is written and looked up in the tenant default locale. Record `metafield` with `"shared": "metafield_definition:import.key"` (the payload `marker.shared`) and `"ref": "import.key"`.
7. **Options**: `list_product_options` on the product first (after an adoption or a partial failure some exist). For each missing option of the payload `options`, `create_product_option` (`path.productId`, `title`, `position`), then `create_option_value` per missing value (`value`, `position`, `productOption` = the option IRI). Record `product_option` and `option_value` items.
8. **Variants**: for each variant of the payload `variants`, `list_variants` with `query.sku = <sku>` (partial match: only a returned `sku` exactly equal counts): on this product, record it per the created/reused rule; on another product, fail this product with a clear error. Else `create_variant` (`path.productId`, `sku`, `barcode`, `optionValues` = IRIs of the option values named in `option_values`, the n-th name belonging to the n-th option). Record `variant`.
9. **Taxonomy and collections**: nothing to call, `product.body` already held `category`, `attributes` and `collections` at creation. Record `{"kind": "taxonomy_link", "iri": "<product iri>#taxonomy", "status": "created", "module": "taxonomy"}` when the body had a `category` or `attributes`, and `{"kind": "collection_link", "iri": "<product iri>#collections", "status": "created", "module": "collections"}` when it had `collections`. A product found by marker or adopted (steps 2 to 4) without them: `get_product`, then `update_product` with the payload `category` and `attributes`, and `collections` = existing + payload ones (merge-patch replaces arrays), then record the links.
10. **Metafields**: for each entry of the payload `metafields` (values, then the metaobject references), `call_operation list_metafields` on `products/<id>`: a metafield with this definition exists -> record it per the created/reused rule; else `call_write_operation create_metafield` `{"path": {"ownerResource": "products", "ownerId": <id>}, "body": <entry body>}`, copied verbatim. Record `metafield` with module `metafields` (`metaobjects` for a reference metafield), `"ref"` = the entry `key` and `"shared"` = the entry `shared`.
11. **Sale offers**: for each entry of the payload `prices`, replace `<variant IRI of <sku>>` in its body with the IRI of the variant with that SKU (step 8). `call_operation list_sale_offers` with `query.variant` = that IRI and `query.country` = the body `country`: an offer exists -> record it per the created/reused rule above (an offer this migration created before a crash stays `created`); else `call_write_operation create_sale_offer` `{"body": <entry body>}`, copied verbatim. Record `sale_offer` with module `prices` and `"ref"` = `<sku>:<country code>` (the entry `sku` and `country`).
12. **Description check**, only when the handle is in `<dir>/verify-sample.json` and the product was created in this run: `get_product`, write its `description` to `<work dir>/readback.txt` with a quoted heredoc, as the JSON string literal of the response (quotes and escapes included), then `python3 $SKILL/scripts/verify.py <dir> <handle> --field description --readback-file <work dir>/readback.txt`. Exit 0: `"verify": "ok"`. Exit 1: `update_product` once with the payload description, read back and verify again: `"fixed"` if it now matches, else `"mismatch"` (the product stays `created`). Add the `verify` key to the result line.
13. **Result**: write the line to `<work dir>/line.json` with a quoted heredoc, then `python3 $SKILL/scripts/state.py result <result file> --json-file <work dir>/line.json`. Line: `status: created`, the product IRI and all items, including a `product` item for the product itself. Store every `@id` exactly as the API returned it (option values are not nested under the product, options and variants are): `state.py result` rejects IRIs that are not `/api/<resource>/<uuid>`. On an unrecoverable error: `status: failed`, the error message, and the items created so far. Then go to the next handle: one failure never stops the worklist.

**Limits.** Every MCP argument is written by the model, even when copied from `payload.py`: invisible characters can still be dropped or replaced, and a retyped IRI can still be wrong. `payload.py` escapes, `verify.py` samples and detects, `state.py result` rejects malformed IRIs: this reduces and detects drift, it cannot guarantee a byte-exact copy. The final report shows the verification counts.

## Worker MCP rules

Every worker prompt includes this block as is: `prompts.py` puts it in place of `{{MCP_RULES}}` in the product workers (`## Worker prompt template`, module-only and update runs included, `references/phases.md` `## Update worker`) and the shared elements worker; the prompt of the read-only snapshot worker (`references/phases.md` step 8) includes it too. In sequential mode, follow it yourself too.

````
MCP rules:
- Tools: the Flowkiwi MCP tools may be deferred: load them first (ToolSearch in Claude Code, with the client prefix such as `mcp__flowkiwi__`; your client's tool search otherwise) before concluding a tool is missing. Run describe_operation before the first call of each operation run through call_operation or call_write_operation (path, query and body arguments).
- Errors: a timeout, an HTTP 5xx and `rate limit exceeded` (HTTP 429) are handled alike: wait with `sleep 5`, then `sleep 15`, then `sleep 45` between attempts, and look up before any retry of a write (the first attempt may have gone through). Still failing after that: fail the item (the product, or the shared entry) with the error and go on.
- Schema refusal: a schema or validation refusal (HTTP 400 or 422, "invalid", "expected string", ...) on a payload printed by a script fails the item with the error message. Never change a value, a type or a format to make it pass: the script output is the decision, the developer fixes the mapping.
````

## Verify

After the pilot, for each pilot product, read only the compared fields and compare them by script, never by reading large responses (a `list_products` with `attributes` on 5 products is about 50 000 characters, beyond what is shown):

1. `get_product` on its IRI with `properties[]` limited to the compared fields (`title`, `description`, `status`, `category`; check the argument with `describe_operation`). Write the `title` to `<dir>/tmp/verify/<handle>-title.txt` and the `description` to `<dir>/tmp/verify/<handle>-description.txt`, each as the JSON string literal of the response with a quoted heredoc, then `$S/verify.py <dir> <handle> --field title --readback-file <dir>/tmp/verify/<handle>-title.txt` and the same with `--field description` (exit 0: match).
2. `call_operation list_product_variants` with `properties[]` `sku` and `barcode` (every page), and `list_product_options`: write them to a file and compare them with the `options` and `variants` of `$S/payload.py <dir> <handle>` by a short script (SKU, barcode and option values per variant), not by eye.

Show the comparison to the developer: the matches as counts, every mismatch with its handle, field, expected and read values.
