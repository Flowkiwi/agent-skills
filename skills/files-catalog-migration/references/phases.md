# Later phases

A later phase applies the client's answers or a new file delivery, in place, to the catalog this migration created: `diff.py` compares the payloads of the regenerated structured files with what the last import wrote (`<dir>/diff.json`), and update workers apply that difference. `$S` is `python3 $SKILL/scripts` and `<dir>` the workspace. Only items recorded `created` in `state.json` are updated, archived or deleted; a reused product or child is never written.

## Update worker

**Worklists.** Once the dry-run of the phase is approved: `$S/state.py worklists <dir> --workers 4 --update` (default 4, at most 6). It reads `<dir>/diff.json`, refused when it was computed for another phase (`diff.json is from phase <n>, run diff.py again`), and prints the `pass` it selected and the handles `skipped` with their reason. Repeat worklists, workers (SKILL.md "Running workers") and `$S/state.py merge <dir>` until it selects no product. Each call returns the first pass with work left:

1. `deletions`: the rekeyed products (diff.json `removal` `delete_rekeyed`: always deleted, never archived, and only after decision `confirmed_rekey` of the phase) and the products still holding a SKU that moves to another product (`moved` `from`: their update deletes that variant). They are merged before any product receiving those SKUs is updated or created: a SKU exists only once in Flowkiwi.
2. `updates`: the other `changed` handles, then the `removed` ones, with decision `removed_action` of the phase (`archive` or `delete`; an `already_archived` handle only for `delete`). A blocked rekey (`removal` `archive_blocked`, listed in `blocked_rekeys`) is always archived, never deleted, whatever `removed_action` says: its SKUs would be lost. A product whose update left `deferred` creations (its new SKU was still held by another product) is selected again once that SKU is free, for a second pass.

Never selected, and listed in `skipped`: the `unmanaged` handles; a changed or removed handle of diff.json `conflicts` (modified in Flowkiwi since the last import) without decision `force_update` of the phase; a deletion of SKUs whose receiver has such a conflict; a product receiving a `moved` SKU this migration never deletes (its `from` is `unmanaged`, or holds it as a reused variant); a failed update (`--retry-failed` to try again); a product whose deferred SKU is still held. A handle already done in this phase is not selected again, so a stale `diff.json` never repeats an update. Every deletion of a pass goes to the same worker: `state.py deleted` writes `state.json`, one writer at a time.

Then the creations of the new handles: `$S/state.py worklists <dir> --workers 4` (`references/create.md` steps 4 and 5). In a later phase it holds back, in `skipped`, a new product whose SKU is still a created variant of another product: run the update passes first.

**Prompt.** The template of `references/create.md` `## Worker prompt template`, with `{{PER_PRODUCT}}` built from three parts, in this order, with `$S` replaced by `python3 <skill path>/scripts`, `$SKILL` by the skill path and `<dir>` by the workspace (workers only see the prompt):

- this note: `Update run (later phase): every product of your worklist already exists in Flowkiwi: its IRI is products.<handle>.iri in the state file and its children are its items there (ref names them). It replaces five rules above. The payload command: build every MCP argument from $S/payload.py <dir> <handle> --update (it reads <dir>/diff.json too). The line format: the line format above, with "status": "updated", "archived" or "failed", the product "iri", in "items" only the items created or found in this run, and "deleted": [every IRI deleted or archived in this run]. Exactly one result line per handle: a product deleted by its delete action writes no line when every step succeeded. The state file is read only: the delete action records its deletions with $S/state.py deleted, the only write to it. Never modify or delete: you update, archive or delete the IRIs payload.py --update prints, and nothing else. They are items this migration created. When done, reply with 3 lines only: handles processed, updated/archived/deleted/failed counts, failed handles with a short reason.`
- the **Created vs reused** paragraph of `references/create.md` `## Per product`;
- the procedure below, from **Plan** to the end of this section.

**Plan.** For each handle of the worklist, in order: run `$S/payload.py <dir> <handle> --update`. If it fails, fail the product with its message: never guess a value. It prints the `action` and its operations; copy every value verbatim (keep `\uXXXX` escapes as is in the JSON arguments). Only IRIs returned at runtime (new options, option values, variants) are added by you. Run `describe_operation` once on each operation before its first call (path argument names) and adapt; do not guess. After an error or a timeout on a write, read the item again (`get_*` or `list_*`) before retrying once: an update already applied reads its new value, a deletion already done reads 404. A 404 on a deletion counts as deleted (gone with its parent). A 409 or any other error: fail the product with the error, the items created so far and the IRIs deleted so far.

**`"action": "update"`**, in this order, each group only when printed:

1. `product` (not null): `update_product` on the product IRI with `product.body` as printed. It is a merge-patch: only the printed fields change, `null` clears a field, `attributes` and `collections` are printed whole and replace the existing lists.
2. `options.create`: `list_product_options` on the product first. For each missing option, `create_product_option` (`path.productId`, `title`, `position`), then `create_option_value` per missing value (`value`, `position`, `productOption` = the option IRI). Record `product_option` (ref: the title) and `option_value` (ref: `<title>:<value>`) items, module `core`.
3. `options.values_create`: `list_product_options` first; for each value missing under its option, `create_option_value` (`value`, `position`, `productOption` = `option_iri`). Record `option_value` items.
4. `variants.delete`: `delete_variant` on each `iri` (its sale offers go with it). Add the IRI to `deleted`.
5. `variants.update`: `update_variant` on each `iri` with `body`; with `option_values`, also `optionValues` = the IRIs of the named values, the n-th name belonging to the n-th option (from the `option_value` items of the state, or created at steps 2 and 3).
6. `variants.create`: for each, `list_variants` with `query.sku = <sku>` (partial match: only a returned `sku` exactly equal counts). On this product: record it per the created/reused rule. On another product: fail the product with a clear error naming that product (`payload.py --update` already left out, in `deferred`, every SKU waiting for a deletion of this migration: a printed creation never waits). Not found: `create_variant` (`path.productId`, `sku`, `barcode`, `optionValues` as in step 5). Record `variant` (ref: the SKU), module `core`.
7. `options.values_delete`, then `options.delete`: `delete_option_value` on each `iri`, then `delete_product_option` on each `iri`. Add the IRIs to `deleted`.
8. `metafields.delete`: `delete_metafield` on each `iri`. `metafields.update`: `update_metafield` on each `iri` with `body`. `metafields.create`: `call_operation list_metafields` on `products/<id>`: a metafield with this definition exists -> record it per the created/reused rule; else `call_write_operation create_metafield` `{"path": {"ownerResource": "products", "ownerId": <id>}, "body": <entry body>}`. Record `metafield` with module `metafields` (`metaobjects` for a reference metafield), `"ref"` = the entry `key`, `"shared"` = the entry `shared`.
9. `prices.delete`: a sale offer has no delete operation: `update_sale_offer` on `iri` with `{"status": "/api/statuses/ARCHIVED"}`, except an offer of a variant deleted at step 4: it is already gone, do not call (a 404 there counts as deleted too). Add the IRIs to `deleted`. `prices.update`: `update_sale_offer` on each `iri` with `body`. `prices.create`: replace `<variant IRI of <sku>>` in the body with the IRI of that variant (state item or step 6), `call_operation list_sale_offers` with `query.variant` = that IRI and `query.country` = the body `country`: an offer exists -> record it per the created/reused rule; else `call_write_operation create_sale_offer` `{"body": <entry body>}`. Record `sale_offer` with module `prices` and `"ref"` = `<sku>:<country>` of the entry.
10. `deferred`: nothing to call. Each SKU is still a variant of `held_by`; a later pass creates it, with its prices, once that deletion is merged.

Line: `"status": "updated"`, even when only `deferred` was printed.

**`"action": "archive"`**: `update_product` on the product IRI with `product.body` (status ARCHIVED). Line: `"status": "archived"`, `"items": []`, `"deleted": []`.

**`"action": "delete"`**: walk `steps` in order (children first), each with the operation of its `kind`: `sale_offer` `update_sale_offer` with `{"status": "/api/statuses/ARCHIVED"}` (skip it when its variant is deleted in this run: it goes with it), `metafield` `delete_metafield`, `variant` `delete_variant`, `option_value` `delete_option_value`, `product_option` `delete_product_option`, `taxonomy_link` and `collection_link` nothing (they go with the product), `product` `delete_product` (refused with 409 while a variant remains). A 404 counts as deleted. Once the product is deleted, every step IRI is deleted (its children went with it): write them as a JSON array to `<work dir>/deleted-<handle>.json` with a quoted heredoc, then `$S/state.py deleted <dir> --iris-file <work dir>/deleted-<handle>.json`, and write no result line. A step refused (409 or another error): stop, record the IRIs deleted so far the same way, then a `"status": "failed"` line with the product `iri`, the error and `"items": []`.
